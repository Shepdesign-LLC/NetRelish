# P4 Stage A — make local writes syncable

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every local write stamps per-field timestamps, every delete becomes a tombstone, and no read returns tombstoned rows — with the app behaving exactly as it does today.

**Architecture:** One `stamp` helper pair that all writes route through, so `field_ts` is correct by construction rather than by 27 call sites remembering. Deletes become `UPDATE … SET deleted_at`, which forces a matching change to the FTS triggers and to every `SELECT`.

**Tech Stack:** SQLite via `tauri-plugin-sql`, TypeScript, Rust (sqlx).

**Spec:** `docs/superpowers/specs/2026-08-19-p4-mac-sync-design.md` §3

**This stage is invisible.** Nothing syncs yet. Success means the app is unchanged from a user's point of view while every write now carries the metadata sync will need.

## Verified before planning

Counted against the shipped app, not assumed:

- **27 write sites in `apps/desktop/src/lib/db.ts`** — 22 inserts/updates, 5 deletes at lines 169 (jars), 381 and 533 (tabs), 585 (recipes), 743 (item_labels).
- **2 Rust writes** in `extract.rs` (lines ~145 and ~154), both `INSERT … ON CONFLICT(url) DO UPDATE` — upserts, which must stamp differently per branch.
- **28 `SELECT`s** in `db.ts`, all of which must learn to filter tombstones.
- Local schema has **no** `updated_at` / `deleted_at` / `field_ts` on any table.
- Migrations run to `003_engine.sql`; the next is `004`.

**The FTS trap.** `items_fts_au` fires `AFTER UPDATE` and re-indexes the row. Tombstoning via `UPDATE` therefore leaves the item in the FTS index, so `⌘K` keeps finding "deleted" items and deleting appears to do nothing. The trigger must be replaced, not just added to.

```sql
-- P4 Stage A. Sync metadata on every syncable table.
--
-- Local timestamps stay epoch MILLISECONDS, matching the existing convention.
-- The sync layer converts to timestamptz at the boundary and nowhere else.

ALTER TABLE jars                ADD COLUMN updated_at INTEGER;
ALTER TABLE jars                ADD COLUMN deleted_at INTEGER;
ALTER TABLE jars                ADD COLUMN field_ts   TEXT NOT NULL DEFAULT '{}';

ALTER TABLE items               ADD COLUMN updated_at INTEGER;
ALTER TABLE items               ADD COLUMN deleted_at INTEGER;
ALTER TABLE items               ADD COLUMN field_ts   TEXT NOT NULL DEFAULT '{}';

ALTER TABLE tabs                ADD COLUMN updated_at INTEGER;
ALTER TABLE tabs                ADD COLUMN deleted_at INTEGER;
ALTER TABLE tabs                ADD COLUMN field_ts   TEXT NOT NULL DEFAULT '{}';

ALTER TABLE labels              ADD COLUMN updated_at INTEGER;
ALTER TABLE labels              ADD COLUMN deleted_at INTEGER;
ALTER TABLE labels              ADD COLUMN field_ts   TEXT NOT NULL DEFAULT '{}';

ALTER TABLE recipes             ADD COLUMN updated_at INTEGER;
ALTER TABLE recipes             ADD COLUMN deleted_at INTEGER;
ALTER TABLE recipes             ADD COLUMN field_ts   TEXT NOT NULL DEFAULT '{}';

ALTER TABLE suggestion_feedback ADD COLUMN updated_at INTEGER;
ALTER TABLE suggestion_feedback ADD COLUMN deleted_at INTEGER;
ALTER TABLE suggestion_feedback ADD COLUMN field_ts   TEXT NOT NULL DEFAULT '{}';

-- item_labels is a pure join table: presence is the only fact, so there is
-- nothing to merge field-by-field and no field_ts. It still needs a tombstone,
-- or a label removed on one device returns from a device that never heard.
ALTER TABLE item_labels         ADD COLUMN updated_at INTEGER;
ALTER TABLE item_labels         ADD COLUMN deleted_at INTEGER;

-- embeddings deliberately gets nothing and never syncs: local vectors are
-- MiniLM, the server's are Voyage at a different dimension. Not comparable.

-- Backfill so existing rows sort correctly on the first sync.
UPDATE jars                SET updated_at = COALESCE(updated_at, created_at);
UPDATE items               SET updated_at = COALESCE(updated_at, touched_at, created_at);
UPDATE tabs                SET updated_at = COALESCE(updated_at, touched_at, opened_at);
UPDATE labels              SET updated_at = COALESCE(updated_at, strftime('%s','now') * 1000);
UPDATE recipes             SET updated_at = COALESCE(updated_at, strftime('%s','now') * 1000);
UPDATE suggestion_feedback SET updated_at = COALESCE(updated_at, at);
UPDATE item_labels         SET updated_at = COALESCE(updated_at, strftime('%s','now') * 1000);

CREATE INDEX idx_items_sync ON items (updated_at);
CREATE INDEX idx_jars_sync  ON jars  (updated_at);
CREATE INDEX idx_tabs_sync  ON tabs  (updated_at);

-- THE FTS FIX.
-- items_fts_au fires AFTER UPDATE and re-indexes the row. Once a delete is an
-- UPDATE that sets deleted_at, a tombstoned item would STAY in the FTS index
-- and ⌘K would keep finding it — deleting would appear to do nothing.
-- Replace the trigger so it removes the old entry always and re-inserts only
-- while the row is alive.
DROP TRIGGER IF EXISTS items_fts_au;
CREATE TRIGGER items_fts_au AFTER UPDATE ON items BEGIN
  INSERT INTO items_fts(items_fts, rowid, title, body)
    VALUES ('delete', old.rowid, old.title, old.body);
  INSERT INTO items_fts(rowid, title, body)
    SELECT new.rowid, new.title, new.body WHERE new.deleted_at IS NULL;
END;
```

- [ ] **Step 5: Prove the FTS trigger fix works**

This is the trap the migration exists to close, so test it explicitly:

**The obvious test does not work.** `items_fts` is an FTS5 *external-content*
table: a scan without `MATCH` is planned as `SCAN items_fts VIRTUAL TABLE`,
which reads column values back from `items`. So joining `items_fts` to `items`
on rowid returns every live row regardless of what the index holds — it
measures the content table, not the index, and reports the same number whether
the trigger fix is present or absent.

Only a `MATCH` query touches the index. Use a before/after control:

```bash
sqlite3 /tmp/nr-stage-a.db "SELECT rowid FROM items_fts WHERE items_fts MATCH 'brine';"
# note the rowids, pick one, then:
sqlite3 /tmp/nr-stage-a.db "UPDATE items SET deleted_at = 1 WHERE rowid = <ROWID>;"
sqlite3 /tmp/nr-stage-a.db "SELECT rowid FROM items_fts WHERE items_fts MATCH 'brine';"
```
Expected: that rowid is present before and **absent after**. Setting
`deleted_at` back to NULL should restore it. Finish with
`INSERT INTO items_fts(items_fts) VALUES('integrity-check');` — it must pass,
proving index and content table are still consistent.

### Task 2: The stamp helpers

**Files:** Create `apps/desktop/src/lib/stamp.ts`

This is the point of the whole stage. If `field_ts` depends on 27 call sites each remembering, it will be wrong within a month.

- [ ] **Step 1: Write the helpers**

```ts
/**
 * Field-level sync stamps.
 *
 * Every local write goes through here. `field_ts` maps column name -> epoch ms
 * of that column's last write, and the server merges field-by-field against it
 * (see supabase/migrations/0006). A write path that builds its own SQL without
 * these helpers is a bug: its fields will look infinitely old and always lose.
 */

/** Columns that are sync metadata, never themselves stamped. */
const META = new Set(["id", "updated_at", "deleted_at", "field_ts"]);

export interface Write {
  cols: string[];
  placeholders: string;
  vals: unknown[];
  setClause: string;
}

/** Build an INSERT's columns/values, including sync metadata. */
export function insertWrite(
  fields: Record<string, unknown>,
  now = Date.now(),
): Write {
  const ts: Record<string, number> = {};
  for (const k of Object.keys(fields)) if (!META.has(k)) ts[k] = now;

  const all = { ...fields, updated_at: now, field_ts: JSON.stringify(ts) };
  const cols = Object.keys(all);
  return {
    cols,
    placeholders: cols.map((_, i) => `$${i + 1}`).join(", "),
    vals: Object.values(all),
    setClause: cols.map((c, i) => `${c} = $${i + 1}`).join(", "),
  };
}

/** Build an UPDATE's SET clause, merging new stamps over the previous ones. */
export function updateWrite(
  fields: Record<string, unknown>,
  prevFieldTs: string | null | undefined,
  now = Date.now(),
): Write {
  let ts: Record<string, number> = {};
  if (prevFieldTs) {
    try {
      ts = JSON.parse(prevFieldTs) as Record<string, number>;
    } catch {
      ts = {}; // corrupt stamp loses to anything; better than throwing mid-write
    }
  }
  for (const k of Object.keys(fields)) if (!META.has(k)) ts[k] = now;

  const all = { ...fields, updated_at: now, field_ts: JSON.stringify(ts) };
  const cols = Object.keys(all);
  return {
    cols,
    placeholders: cols.map((_, i) => `$${i + 1}`).join(", "),
    vals: Object.values(all),
    setClause: cols.map((c, i) => `${c} = $${i + 1}`).join(", "),
  };
}

/** A tombstone. Deletes never remove rows — an absent row cannot replicate. */
export function tombstone(prevFieldTs: string | null | undefined, now = Date.now()): Write {
  return updateWrite({ deleted_at: now }, prevFieldTs, now);
}
```

### Task 6: The Rust upserts

**Files:** Modify `apps/desktop/src-tauri/src/extract.rs` (~lines 145, 154)

Both are `INSERT … ON CONFLICT(url) DO UPDATE SET …`, so a single statement takes either branch and must stamp correctly for whichever it took.

- [ ] **Step 1: Stamp both branches**

On insert, `field_ts` covers every column supplied. On conflict, only the columns the `DO UPDATE` actually sets should be re-stamped, merged over the existing stamp. SQLite can do this inline with `json_patch`:

```sql
ON CONFLICT(url) WHERE url IS NOT NULL DO UPDATE SET
  title      = excluded.title,
  body       = excluded.body,
  touched_at = excluded.touched_at,
  updated_at = excluded.updated_at,
  deleted_at = NULL,
  field_ts   = json_patch(items.field_ts, excluded.field_ts)
```

`deleted_at = NULL` is deliberate: re-visiting a URL the user deleted should bring it back, because that is what `⌘J` on it means. Note it in a comment so it reads as a decision.
