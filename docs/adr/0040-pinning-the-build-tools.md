# ADR 0040 — The build tools are pinned to bytes, not to Homebrew

**Status:** proposed · **Date:** 2026-11-26 · **PR:** ci(project): pin XcodeGen by version and hash

## What happened

On 2026-11-26 the "Generated files match their sources" job passed on PR #115 and failed on
PR #118 three minutes apart. Both runs held a byte-identical `project.yml` and a
byte-identical `NetRelish.xcodeproj`. Neither pull request touched either file.

The two runners were holding two different XcodeGens. 2.48.0 writes
`buildArchitectures = "Automatic"` into every `.xcscheme`; 2.46.0 does not. The job
regenerates the project and diffs it against the committed one, so the tool decided the
verdict, and the error it printed — "NetRelish.xcodeproj is stale — run
scripts/gen-project.sh" — named the one thing that was not wrong.

`brew install xcodegen` is the cause. It is a no-op when **any** version is already in the
runner image's Homebrew cache, so it never establishes a version; it only confirms that some
XcodeGen exists.

## Why `brew upgrade` is not the fix

The first attempt at this pin ran `brew upgrade xcodegen` and then asserted the version. That
is not a pin. It tracks Homebrew's formula HEAD, which moves on its own schedule, so the next
upstream bump turns a green pull request red for a change it never made — the same ambush,
rescheduled. It also cannot reach a version Homebrew has moved past: the assertion for 2.48.0
failed on a runner whose Homebrew serves 2.46.0, and no amount of upgrading would have fixed
it.

## The decision

`scripts/xcodegen-version.txt` records the version **and** the SHA-256 of upstream's release
archive. `scripts/xcodegen.sh` downloads that archive from the project's own GitHub release,
refuses it if the hash does not match, extracts it to a per-version directory, and prints the
path to the binary. Homebrew is not involved. Callers use the path:

```sh
XCODEGEN=$(scripts/xcodegen.sh)
"$XCODEGEN" generate --quiet
```

The pin is **2.46.0**, because the committed `NetRelish.xcodeproj` carries no
`buildArchitectures` and so was generated by 2.46.0. The project therefore needs no
regeneration: the pin names the version it already matches. Moving to a new XcodeGen means
changing both fields, running `scripts/gen-project.sh`, and committing the project it writes
in the same commit — they travel together or the check means nothing.

## What this costs

A 4.3 MB download per run instead of a cache hit, once per runner. Against it: the check
stops being a coin flip, and a red "stale project" now means the project is actually stale.

## A trap this uncovered

`workflow_dispatch` reads the workflow from the ref it is dispatched on, not from the
`branch` input. A regenerate run started against `main` executes **main's** copy of the steps
while checking out the branch — so an edit to `regen-project.yml` takes effect only once it is
on main. Run 27 ran main's unpinned `brew install` against the branch's pinned scripts and
tripped the pin's own assertion. The scripts come from the branch; the steps do not. This is
written into the workflow's header.
