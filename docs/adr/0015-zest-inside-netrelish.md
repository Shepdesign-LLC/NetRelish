## Design

**Only the free tools, offline, in their own window.** Studio, ZestMail, Zest MD and ZestImage ship inside the signed app and open from Window › Zest. They don't open as Bench tabs. So they never sink into Brine, they aren't in any jar, and they can't be sealed. The window has no keyboard shortcut, because ⌘⇧Z is Redo.

- **One file per tool, switched at runtime.** Each tool checks `IN_APP` (true on the `zest:` protocol or when the bridge is present). When it's true, the tool:
  - skips its service worker
  - drops "Draft with Claude"
  - removes pricing links and Upgrade prompts (App Store rule 3.1.1)
  - greys out the cloud features with one line of explanation

  `build.sh --app` leaves out store/, pricing/ and api/. DOMPurify, KaTeX, Mermaid and the curated fonts are copied into the repo for every surface. That costs nothing on the web, because zest.netrelish.com isn't deployed yet.
- **Pinned and generated.** `Resources/Zest/` is generated and committed. `VENDOR.lock.json` records each library and font: version, source, SHA-256 and licence. CI rebuilds the folder, diffs it, and fails if the DOMPurify version in the md tool's script tag doesn't match the lock. project.yml adds Resources/Zest as a folder reference, because four `index.html` files would collide in a flat group. The project is regenerated with XcodeGen, so the CI project diff passes. No new entitlements.
- **Host (1.1, about 300 lines of Swift):**
  - A read-only `zest://app` scheme handler that refuses any path outside the Zest folder.
  - One fixed `WKWebsiteDataStore` for Zest that is never a jar's store.
  - A content rule list that blocks every http(s), ws(s) and file load, plus a Content-Security-Policy as a second layer.
  - A clicked web link opens as an ordinary page load in the active jar.
  - File inputs use the native open panel. Exports go through `WKDownload` to the native save panel.
- **No bridge in 1.1.** A frozen stub, `window.netrelish = {version:'0', host:'app', network:false}`, has no methods, so a page has nothing to call. A test checks that the stub is never in a jar's web view.
- **Bridge in 1.2.** It adds files, clipboard, toast, events, and studio-to-tool handoff. Every message must come from the main frame on the `zest:` origin. It has no `license()` and no network calls, ever.
- **Seal, Capture and Fill from Me are disabled while a Zest window is in front.** Without this, ⌘S in ZestMail would seal a page in the main window.
- **Brand.** The tool content keeps its own look, the same way the Bench never restyles a page. The window frame around it follows the manifest: neutral surfaces, SF Symbols, no relish.

Cloud Zest stays on zest.netrelish.com permanently: accounts, the license token, Stripe, sync, S3 publishing, test sends and the Claude proxy.

## Rule check

- **NN1:** No new kind. Save to jar uses `file`.
- **NN2/NN3:** The Zest window is not a tab, so it can't sink. Seal is disabled while it's in front.
- **NN4:** Model drafting is removed from the app. Zest output reaches Recipes and models only after it's saved to a jar and sealed.
- **NN5:** Held word for word. No endpoint is added. Offline is enforced in three layers, because the CodeQL gate only reads Swift:
  1. a static scan that fails on any http(s) URL in a load position and on the strings "pricing" and "Upgrade"
  2. a Playwright stage that fails on any request that isn't to localhost
  3. the runtime rule list

  The privacy page stays true. So does the roadmap's "there's no NetRelish account."
- **NN6:** Zest has its own store, which is not a jar's. Jar cookies never reach a tool.
- **NN7:** Zest's word "Recipes" (spec §2.1) is not used in the app.
- **NN8:** Zest code becomes part of the MIT app. Add a root LICENSE and a NOTICE covering DOMPurify (Apache-2.0/MPL-2.0), KaTeX and Mermaid (MIT), and the fonts (OFL).

## Risks

1. **Storage on `zest://`.** If WebKit doesn't persist storage for the custom scheme, the 1.2 storage bridge moves into 1.1, at about +3 days. `file://` is not a fallback, because its null origin breaks storage.
2. **App Review.** A leftover Upgrade or pricing link fails rule 3.1.1. Downloaded code would fail rule 2.5.2, which is why there are no registry updates.
3. **Bundle size.** Estimated at 8–15 MB. Measure it in the spike and propose a size budget.
4. **Two Zests.** The web copy and the app copy keep separate data. They meet only through export and import, and the release notes must say so.
5. **Calendar.** The optional pre-launch work stops the moment App Store prep (P5) needs the time.

## Ryan decided (Nov 1)

- **Timing and scope, as planned:** Zest arrives in 1.1 (January), not in the Dec 14 build. In the app, Zest is the free tools working offline. Sign-in, sync, publishing, test sends and Claude drafting stay on zest.netrelish.com. Zest opens in its own window (Window › Zest), not as tabs in a jar.

## Ryan decides (still open)

1. Inside the Zest window, can the tools keep their own colors and type, with NetRelish's plain frame around them?
2. Can the fruit icons appear in NetRelish's menus, or do the menus use plain system icons?
3. Zest calls saved layouts "Recipes." In NetRelish, a Recipe always runs in Shortcuts. Should Zest pick another word?
4. Are the names Zest, ZestMail, Zest MD and ZestImage, and the fruit icons, reserved like the NetRelish logo?
5. Later: should NetRelish Pro also unlock Zest's offline extras, such as batch images, SVG export and the brand sheet?
6. Until 1.1, Zest changes won't show in the app. Are screenshots in chat OK as the demo for those PRs?
